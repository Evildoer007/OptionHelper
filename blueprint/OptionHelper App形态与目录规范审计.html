OptionHelper App Agent Runtime专项设计草案

定义OptChat如何在权限和金融事实约束下调用现有Capability，并明确Recommender、工具模块、OptDesk和App Agent之间的唯一运行关系。

设计目标面向结构化期权研究的混合型Agentic AI应用
文档状态有价值的架构审计草案，不是最终实施规范
使用边界：本文只负责App Agent Runtime专项设计。总目录、金融模块实现、Knowledger内容和发行规则仍由总蓝图及各模块规范管理。

2App形式定位

AI Agent是系统中的具体决策主体；Agentic AI是包含Agent、Workflow、专业工具、知识、人工审批和治理机制的完整系统范式。两者不是互斥分类。

产品入口

OptChat负责自然语言交互；OptDesk负责人工操作与AI辅助。

Agent Runtime

理解目标、构建上下文、路由、调用工具、观察结果并决定下一步。

Agentic Workflow

Recommender负责Intent、Research、Critic、Approval和Executor。

专业能力

DataFetcher、Payoffer、Pricer、Backtester、Reporter和Designer。

事实与治理

Knowledger、ResolvedContract、Store、权限、审计和版本清单。

正式定位：OptionHelper不是一个单独Agent，而是以OptChat Agent为智能入口、以确定性金融模块为执行能力、以OptDesk承载人工审核的混合型Agentic AI应用。
组成准确定位是否Agent
OptChat与App Agent Runtime理解请求、管理上下文并驱动工具循环是，完成闭环后属于AI Agent
Recommender推荐状态机与Agentic Workflow可由单Agent或多Agent执行
Payoffer、Pricer、Backtester确定性金融计算模块否
DataFetcher、Reporter、Designer数据与交付能力否
Knowledger受治理的产品知识和机器规则源否
OptDeskHuman-in-the-loop专业工作台不是纯Agent界面

3当前已有能力

当前项目并不是从零开始。Recommender、ToolGateway、ToolDispatcher、权限、任务、Store和七个能力模块已经存在。缺口集中在OptChat主消息链没有把这些能力组织成唯一Agent循环。

4必须解决的问题

以下六项是App从AI辅助工作台升级为受控Agentic AI应用的实施问题。每一项都必须有代码、权限和Eval证据。

P0-1
OptChat缺少唯一外层Agent循环

ConversationService只完成一次模型调用，没有结构化决策、工具Observation、退出条件和多轮状态。

解决方式

由App Agent独占外层循环，统一处理final、ask_user、call_tool和request_approval四类动作。

P0-2
存在双重循环风险

如果App Agent调用Recommender freeform，而Recommender又自行调用工具并循环，会产生嵌套决策、重复调用和状态归属不清。

解决方式

App内只调用Recommender固定推荐Workflow。Recommender freeform仅保留给独立Skill场景，不得嵌入App Agent循环。

P0-3
用户经OptChat调用模块的权限未定义

用户不能进入OptDesk，但仍需要通过自然语言调用推荐、损益图、估值、回测和报告。隐藏页面不能替代服务端授权。

解决方式

按身份生成可见Tool Catalog，并在ToolDispatcher再次鉴权。用户只能操作本人Task及其结果，维护动作始终禁止。

P0-4
主Agent缺少受控任务上下文

当前模型只收到本轮消息，缺少历史消息、ResolvedContract、DataAssetRef、ModuleRunRef、审批状态和权限。

解决方式

由ConversationService按最小必要原则组装上下文。金融事实只能来自版本锁定Knowledger和正式引用。

P0-5
App内置Capability可能与Skill产物漂移

当前App内置Capability和dist Skill都能单独通过校验，但content_tree_hash不同，说明两份候选不是同一字节级能力包。

解决方式

App构建只能原样装入刚通过验证的Skill候选，禁止手工修改内置副本；哈希不一致立即阻断构建。

P0-6
Agent Eval不能后补

只测试模块计算不能证明路由、权限、循环终止、缺参追问和金融事实引用正确。

解决方式

每完成一段Agent链路，同步扩展现有workflows、permissions、tools和app_host Eval，未通过不得进入下一阶段。

核心改造目标：不是新增更多Agent文件，而是建立一个权责清楚的App外层循环，并把已有Recommender和工具能力安全接入。

6角色与工具权限

用户权限不是“只能聊天而不能使用模块”。正确含义是用户只能通过OptChat Agent间接使用获准能力，不能进入OptDesk自由操作，也不能执行资料库和默认资产维护。

能力用户经OptChat管理员经OptChat管理员经OptDesk额外门禁

Recommender推荐允许允许允许候选执行前需要确认
DataFetcher允许受限调用允许允许仅获准Provider、资产和时间范围
Payoffer、Pricer、Backtester允许受限调用允许允许直接配置ResolvedContract和输入Schema必须通过
Reporter仅本人Task结果允许允许选择正式RunRef报告发布与文件导出单独授权
Knowledger与默认Payoff维护禁止普通对话禁止仅专门维护流程管理员身份、显式审批和归档

第一层：工具可见性

App Agent只接收当前身份可用的Tool Catalog，模型看不到无权调用的维护工具。

第二层：服务端鉴权

ToolDispatcher必须按identity、task_id和具体action重新检查权限，不能信任模型选择。

第三层：模块校验

模块继续校验ResolvedContract、Config、DataAssetRef和输出路径，权限通过不等于输入有效。

第四层：结果归属

结果绑定tenant_id、principal_id和task_id；用户不能通过路径或RunRef读取其他人的结果。

7实施顺序

阶段1
先锁定Agent协议、权限和Eval基线

定义四类Agent Decision、最大轮次、Observation、审批状态和用户工具权限；同步为现有Eval增加失败用例。

阶段2
完成一个工具的外层闭环

先让OptChat可靠完成Knowledger查询或Payoffer运行，证明上下文、ToolDispatcher、Observation和最终答复完整闭环。

阶段3
接入Recommender固定Workflow

实现AppAgentPort、AppKnowledgePort和AppToolPort Adapter；明确拒绝App场景下的Recommender freeform。

阶段4
覆盖其余模块并统一Desk上下文

三个计算模块和Reporter逐一接入；OptChat与OptDesk共享Task、ResolvedContract、DataAssetRef和RunRef。

阶段5
再接服务器与真实Provider

本地闭环验收后再接远程身份、服务器Store、模型Provider和数据Provider。Multi-Agent只在Eval证明确有必要时引入。

同步开发规则：每个阶段必须同时提交实现、单元测试、权限测试和Agent Eval。Agent Eval不是第五阶段的补充任务，而是每个阶段的完成条件。

8代码位置与Capability一致性

当前顶层目录已经足够清楚。本专项只在现有App目录补最少代码，不新增agents、workflows、tools或memory等泛化顶层目录。

最小文件结构

9完成标准

验收层必须证明的结果
唯一循环OptChat只有App Agent拥有外层会话循环；Recommender固定Workflow执行一次后返回，不进入freeform。
工具与权限用户能经OptChat调用获准模块，但不能进入OptDesk、执行维护动作或访问其他人的Task和RunRef。
上下文模型读取受控任务历史、ResolvedContract、DataAssetRef、RunRef和审批状态，不读取无关全量文件。
金融一致性所有数字来自正式模块及同一ResolvedContract；模型不得生成伪造PV、回测、Greeks或默认图。
CapabilitySkill候选与App内置Capability逐字节一致，content_tree_hash相同，生成副本无手工修改。
错误与退出缺参时追问，权限不足时拒绝，工具失败时不编造，达到最大轮次或重复调用时可靠停止。

10证据与判断口径

ConversationService当前消息链只进行一次ModelGateway调用并保存文本，没有工具循环。
ModelGateway当前只发送本轮用户消息，没有任务上下文、工具定义和Observation。
ToolDispatcher正式工具调度、任务绑定、结果登记和错误处理已经存在，但尚未由OptChat消息链驱动。
ToolGatewayApp到Capability的正式调用边界已经存在，Agent Runtime应复用它而不是直接导入模块。
Recommender Service已经具备固定推荐Workflow和freeform工具循环，因此必须明确App只使用固定Workflow。
Recommender PortsAgentPort、KnowledgePort和ToolPort协议已经存在，当前缺App正式Adapter。
App Capability Manifest当前内置Capability自身校验通过，但与dist Skill的content_tree_hash不同。
当前构建入口最终应由同一已验证Skill候选生成Skill ZIP并原样Stage到App。
OpenAI Agent指南LLM必须管理工作流、动态选择工具并循环至退出条件；单轮LLM应用不属于Agent。
Anthropic Agent工程指南区分预定义Workflow和模型动态控制过程的Agent，支持本报告的分类口径。

最终判断

本文件应保留并作为App Agent Runtime专项设计草案继续修订。实施重点不是重写Recommender、ToolGateway或金融模块，而是建立唯一App外层循环、限定Recommender固定Workflow、落实用户经OptChat受限调用模块的权限、消除Capability副本漂移，并让Agent Eval与每段实现同步交付。上述门禁全部通过后，再把本专项纳入OptionHelper总蓝图。
