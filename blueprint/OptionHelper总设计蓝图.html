OptionHelper总设计蓝图

OptionHelper包含可独立发布的标准Skill与App。Skill以一个可安装的option-helper包承载七个内部能力模块；App在同一已验证能力包外增加账号、权限、模型、数据接口设置、会话、任务、审计以及OptChat、OptDesk壳层，不复制金融逻辑与模块页面。

0. 文档用途、适用边界与阅读方式

0.1 本文定义什么

本文是后续实现、改造、审计和多对话协作的总纲领。它定义每一层谁拥有规则、谁可以读取或写入什么、同一任务如何形成合同和证据、以及模块之间不得互相替代的边界。它不保存65个产品的具体金融条款，也不覆盖已经冻结的OptionLib符号与单产品公式。

推荐阅读顺序：先看第1.1节的全景图，确认“Knowledger与共享运行时→七个内部能力模块→标准Skill或App封装→正式结果与交付”的主线；再按第4至6章核对产品、合同、数据和三项计算；随后阅读第7至12章的Agent、报告、前端、权限、结果与目录；最后以第13章判断当前实现与迁移顺序。后文每章只能细化这条主线，不能另起一套架构。

架构、接口与治理

1.2 两个可独立交付的产品与三种运行入口

OptionHelper提供两种可独立使用的形态：OptionHelper Skill是可直接安装的标准option-helper包；OptionHelper App是在同一已验证Capability外增加自有平台框架的应用。App内部再分为OptChat和OptDesk两种工作模式。

OptionHelper Skill

由Claude、Codex、DeepSeek、Kimi等外部Agent框架发现根SKILL.md。宿主提供模型和对话上下文；标准Skill通过references、scripts和assets提供知识、合同、七模块工具与五个页面。

OptionHelper App产品

自带Identity、Authorization、ModelGateway、Session、Task Runtime、Secret、DataStore、ResultStore、Audit及前端壳层。App使用同一共享能力，不复制产品条款、合同解释器、定价、回测或报告事实。

三种运行入口

外部Skill Host

读取根SKILL.md后按Tool Catalog调用七个内部能力模块。宿主负责通用对话与Agent运行，OptionHelper校验工具输入、写入边界和结果契约。

OptChat

App中的对话工作模式。销售用户和管理员通过App Agent Runtime完成学习、分析、推荐及客户交付。

OptDesk

App中的管理员操作台。支持人工直接运行模块或使用AI辅助；人工操作可以不经过Agent推理，但不能绕过授权、合同解析、工具网关和结果协议。

分类口径：“两个产品”描述交付和部署边界；“三种入口”描述运行时如何进入共享能力。OptChat和OptDesk不是额外产品，外部Skill Host也不是App页面。

1.4 不可违反原则

一套共享核心

OptionReg、ResolvedContract和共享解释器是条款与现金流的唯一执行来源。Skill产品与App产品只能通过发布接口消费，不能形成两套金融实现。

模块并列

Payoffer、Pricer、Backtester可单独运行，共用合同与解释器，但不调用彼此、不拿另一模块结果充当自己的输入。

封装不反向污染

外部Host、OptChat、OptDesk、模型和页面只拥有交互及编排状态；默认资料、市场数据、模块结果和报告均按正式事实对象保存。

2.3 合同指纹、数据谱系、产物哈希与可复现性

contract_fingerprint覆盖影响经济结算的产品编号、标的顺序、币种、价格口径、条款和观察日程。task_id只是组织索引，不是金融一致性的充分条件；同一任务可以包含多个候选，同一冻结合同也可以在受控条件下被不同任务显式复用。

Fexec=SHA-256(Fcontract+Vproduct+Vcatalog+Hinterpreter+Hmodule+Hconfig+Hdata+Vcalendar+Vstandard)

execution_fingerprint只覆盖运行前已经冻结的输入和实现环境。Pricer另纳入model_build_hash与numerical_config_hash；Backtester另纳入metric_profile_hash，但运行后才产生的ledger_hash只能进入semantic_result_hash，不能反向进入执行指纹。跨模块的execution_fingerprint天然不同，Reporter不得要求三模块执行指纹相等；它只核对合同、产品发布、分析基准和数据口径兼容，并分别验证每个ModuleRun自身的执行指纹。

所有哈希先按统一Canonical JSON规则规范字段顺序、浮点、日期、时区、空值和单位，再使用SHA-256；hash_spec_version必须写入清单。哈希分层固定为：semantic_result_hash表示金融事实，presentation_input_hash表示绘图或报告输入，artifact_hash表示具体SVG、HTML或PDF；Designer变化不得改变金融事实哈希，但会形成新的产物哈希。

目录内容树哈希使用独立规范：所有相对路径使用/，Unicode路径规范化为NFC，禁止大小写冲突和符号链接；每个文件按原始字节计算SHA-256，不转换换行，并把{path,size,sha256,executable}按path排序后再计算整树哈希。Capability Manifest自身不进入Capability内容树。App内app-manifest.json在平台签名前生成并由最终代码签名覆盖；签名后的DMG或Windows安装器哈希、签名身份和公证状态只写入版本历史外层的PlatformReleaseManifest，避免修改已签名App形成闭环。

4.1 OptionList、OptionLib、OptionReg的唯一职责

OptionList

人工目录总领。保存中文唯一名称、编号、分类和资料状态，是资料维护和引用的入口。

OptionLib

人类与模型阅读的条款主源。保存唯一数学符号、严格条款、路径、分段函数、默认示例、场景和风险说明。

Payoffer、Pricer、Backtester的唯一机器产品源。保存字段定义、产品默认条款、监测、路径和现金流表达，不保存市场数据或模块配置。

Knowledger是逻辑知识领域，对应references/中的产品资料；它没有独立金融计算入口。每次资料变更先按产品生成不可变的product-version.json，使OptionList片段、OptionLib片段、OptionReg产品块、默认JSON和默认SVG在同一个product_version中原子生效；再由catalog-version.json锁定本次全库检索使用的65个product_version映射。这样Recommender比较多个产品时不会在同一任务中读取不同更新时点。

price_convention必须在合同解析时固定为标准化合同尺度或绝对市场价格尺度。它属于ContractContext与ResolvedContract身份，不是PricingConfig，也不能由页面根据数值大小猜测。

标准化合同尺度

默认令合同参考价S0=100，执行价和障碍在同一100尺度表达。市场固定参考价单独保存在reference_prices，本次市场价格映射为：

St~=100×StmktS0,refmkt

新发合同参考价可以等于估值日市场价；存续合同必须使用合同起始固定价。

绝对市场价格尺度

S0、K及全部价格型障碍直接使用市场点位，合同参考价必须与实际起始参考价一致。固定绝对条款只适合真实单合同入场；滚动多入场回测必须改用标准化模板，否则同一静态执行价和障碍会被错误复用于不同历史价格水平。

无论哪种尺度，估值日Spot和回测结算价格均来自不复权市场价格，再由合同解析器映射到合同尺度；前复权价格只用于Pricer的定价HV和Backtester可选的入场HV分组，不参与任何合同观察或现金流。归一化映射、市场参考价、价格口径和标的顺序必须进入contract_fingerprint及逐笔trade_contract_fingerprint。

ResolvedContract

4.5 观察、监测、路径与现金流解释

Payoffer、Pricer、Backtester共用受限解释器，禁止eval。解释器负责符号绑定、条款约束、观察日历、monitor事实、path条件、case定义域和现金流；它不负责模型选择、数据下载、报告描述或页面展示。同日竞争事件必须直接写成互斥且完整的path条件，例如“KO”“not KO and KI”“not KO and not KI”，并用完整性测试证明唯一命中；不能只依赖≤或<边界符号，更不能由页面临时推断优先级。

Monitor与受限函数集

Monitor只把价格路径和日程转成可复用事实，例如首次触发时点、观察值、区间计数、累计数量、Worst-Of表现或已实现方差。Condition只用这些事实和terms做布尔判断；Case.domain只决定路径内的分段；pnl只生成现金流。禁止monitor直接判断最终经济路径、调用另一个monitor或生成现金流。

受限函数唯一用途关键约束
min、max有序标的表现、阈值或数量的确定性聚合。输入维度和标的顺序固定。
first_time、first_time_after、first_time_before在指定日程和边界内寻找首次满足条件的交易日。找不到时返回受控空值，不能猜测日期。
first_time_levels、schedule_levels、step_levels处理随观察期变化的障碍数组或阶梯水平。日程与水平数组长度必须匹配。
first_time_below_schedule、reset_knockout_time处理按日程变化的敲入或敲出重置规则。优先级和生效时点必须来自路径条件。
first_value取得首次命中时的价格、水平或其他事实。必须与对应first_time引用同一事件。
count、count_until区间计息、观察次数或提前终止前累计次数。观察集合与终止边界显式。
realized_variance按合同约定收益率和年化口径计算已实现方差。价格口径、收益率定义、采样日程和annualization_days固定。
accumulated_quantity按观察结果、倍数和终止事件累计数量。不能把保证金调整当作PnL。
cashcash(t, amount)生成持有方在时点t的合同现金流。金额正负、币种和支付时点明确；不在解释器中折现。

Registry阻断校验

  1. 顶层、产品块和路径块只能出现允许字段，未知字段直接失败。
  2. product_id、中文名称和entry_status完整，且与OptionList唯一映射。
  3. 所有terms键均存在于term_catalog，类型、单位和值域有效。
  4. constraints可计算且默认条款全部满足，覆盖后再次校验。
  5. pricing_methods来自能力枚举，登记闭式时必须存在精确实现绑定。
  6. monitor及公式只能调用白名单函数和已绑定符号，禁止eval和任意Python调用。
  7. paths.condition在全部可达状态上互斥且完整；每条路径的cases.domain同样互斥且完整。
  8. 每个可达分段都能生成可解释现金流，默认示例能逐路径命中；任何失败使该产品不能发布为entry_status=True。

  1. 在OptionList分配唯一product_id和中文名称，确认没有同义重复结构。
  2. 在OptionLib用全项目唯一符号写清条款、观察、事件优先级、路径、分段定义域、持有方现金流和默认示例。

5.1 DataRequest、DataAssetRef与数据谱系

DataFetcher是任意内部模块、Agent、OptDesk或用户请求可调用的通用数据服务，不是Pricer或Backtester的附属脚本。Pricer和Backtester可以请求数据，但不会打开DataFetcher前端，也不会自行持有数据源Token。

DataRequest = { asset_ids, fields, frequency, date_range, adjustment, source_priority, cache_policy } ↓ 权限、字段白名单、额度与缓存覆盖检查 ↓ 本地缓存 / 用户上传 / iFinD / Wind ↓ 标准化、质量校验、谱系登记 ↓ DataFetchRun = { status, request_hash, cache_decision, provider_calls, quota_usage, warnings, error } DataAssetRef = { data_asset_id, storage_ref, media_type, schema_id, asset_ids, normalized_fields, coverage, row_count, price_convention, provider, request_hash, content_hash, lineage, tenant_id, access_scope }

DataFetchRun状态固定为complete、partial、stale、failed、unauthorized或quota_exceeded。Pricer和Backtester只能消费满足本次字段、覆盖、口径和权限要求的complete资产；partial或stale必须由调用者明确接受且在ModuleRun中保留限制，failed、unauthorized和quota_exceeded不可继续计算。

5.2 DataAssetRef、MarketSnapshot与覆盖优先级

DataAssetRef提供经校验的原始市场事实 ↓ MarketSnapshot派生估值日Spot、HV、相关矩阵、利率和分红假设 ↓ PricingConfig仅保存用户或模型的显式override ↓ ResolvedPricingConfig保存最终值、单位和逐字段source

Backtester不使用第二套HistoricalDataRef。BacktestInput中的历史数据就是满足历史覆盖、频率和价格口径要求的DataAssetRef。用户上传与Provider数据不自动混合；若用户明确选择上传文件，该文件经标准化后形成独立DataAssetRef。数据冲突、过期或覆盖不足必须保留状态，由调用者选择补齐或终止。

5.3 缓存、Provider与市场数据口径

规则明确口径
缓存reuse只读复用；extend_only只补缺失区间；force_refresh只允许管理员调用。缓存键至少含资产、字段、频率、复权口径、来源和日期覆盖。
合同与回测价格合同观察、障碍判断、保证金、历史回测结算使用不复权close。数据集只含交易日，不另行处理周末、节假日或顺延。
历史波动率Pricer的定价HV和Backtester可选的入场HV分组均使用前复权adj_close的对数收益率。窗口按5、10、20、60、122、244个交易日选择，并按244个交易日年化；Backtester每笔只可使用entry_date及以前的数据，不将复权价送入合同现金流解释器。
合同计息票息和合同现金流按条款规定的日计数；当前未特别说明时使用实际存续日数除以365。244只用于交易日波动率年化，不用于合同票息。

多标的历史回测由BacktestConfig决定对齐政策；定价相关矩阵的标的顺序必须等于ResolvedContract.underlyings。
数据版本谱系记录拉取时间、供应商、标准化版本、复权与企业行动政策、缺失值和异常值处理摘要。停牌、退市或历史修订不能被“交易日数据”假设掩盖。
数据来源本地缓存优先。用户上传先经过同一标准化与质量校验。iFinD/Wind只在缓存不存在或覆盖不足时按额度下载，并把新增覆盖安全写回缓存索引。

字段标准、观察精度与无前视边界

日线标准数据至少支持date、asset_id、open、high、low、close，以及在资产适用时对应的adj_open、adj_high、adj_low、adj_close；具体ModuleRun只声明并读取自己需要的字段。指数等无需企业行动调整的资产可以使复权字段等于原始字段，但仍须在DataAssetRef中声明复权政策。

OptionReg的observation_price决定合同观察使用close、open、high或low。若合同要求连续或盘中监测，而本次DataAssetRef只有日线，系统只能在产品条款明确允许时建立“日频代理”并把exact_observation=False、代理字段、偏差和风险写入ResolvedContract与ModuleRun；否则返回observation_granularity_unsupported，不能把日收盘近似写成真实连续触发。

任何估值日市场快照只读取valuation_date及以前可见数据；任何历史入场样本的参考价、HV、相关性或其他动态参数只能使用entry_date及以前的数据。entry_date之后的价格只用于实现该笔合同路径和现金流，不能反向进入入场参数、候选选择或模型校准。

5.4 本机到服务器切换、额度、凭据与失败处理

开发期可使用本地CSV和测试Provider，正式期可增加iFinD、Wind或其他Provider，但调用面不变。数据源凭据只能由SecretProvider向受控Provider注入。DataStore根据受控storage_ref读取数据；调用者、网页和模型不得传入任意服务器文件路径。若额度不足、字段无授权、下载失败或数据不完整，DataFetcher返回带原因的失败或缺口状态；调用方不得以旧数据、示例数据或模型猜测替代。

5.5 DataFetcher独立构建规格

DataFetcher只有一个正式服务入口fetch_data(DataRequest, CallerContext)。入口负责按顺序调用校验、缓存解析、Provider、标准化、质量检查和资产登记；每个内部组件只处理一种职责。不得为Pricer和Backtester各写一套下载函数，也不得让HTML直接调用iFinD或Wind。

6.共享合同解释器与三个并列计算模块

80%主执行设计

先解析同一ResolvedContract，再按请求并列运行Payoffer、Pricer和Backtester；三者共用合同解释语义，但各自保存独立ModuleRun。

20%错误边界

输入不完整、方法不支持、数据不足或计算不收敛时明确失败；禁止三模块互相读取对方结果补数。

6.1 共用解释器、输入与ModuleRun协议

Payoffer、Pricer、Backtester是三个并列、可独立运行的内部能力模块：各自拥有module-guide、Manager、页面、服务、核心代码和测试，由根option-helperSkill统一发现和路由。三者共同依赖只读合同对象与受限合同解释器；DataAssetRef只在本次模块确实需要市场或历史数据时传入，Payoffer不因共用协议而被迫读取行情。一次请求可按需运行0至3个模块；三模块均须保存统一ModuleRun信封，至少包括租户、analysis_case_id、模块名、task_id、run_id、可空candidate_id、状态、合同指纹、执行指纹、输入快照、数据谱系、产物清单、结果、限制和对象权限。

共用不等于串行：Payoffer不把图给Pricer当输入；Pricer不调用Backtester；Backtester不读取Pricer的HV、利率或蒙特卡洛结果。它们的共同点是：同一合同应得到同一条款解释、路径判定与现金流语义。

6.2 ModuleRun生命周期、前置条件与失败协议

created → validating → queued → running ↓ succeeded / partial / failed / unsupported / cancelled / timed_out

合法转换固定为：created只能进入validating或cancelled；validating可进入queued、unsupported、failed或cancelled；queued可进入running、cancelled或timed_out；running可进入succeeded、partial、failed、cancelled或timed_out。终态不可原地重启，重试必须创建新run_id。ready只表达依赖已准备，不再作为运行成功状态。

统一Error对象包括error_code、stage、message、retryable、missing_inputs和upstream_refs。succeeded必须有完整Result与ArtifactManifest；partial仅在模块规范列明可交付子结果时允许且只能进入内部材料；failed、unsupported、cancelled和timed_out至少保存manifest、输入快照、合同引用、已知数据引用和Error，不得伪造result.json。

运行对象关键前置条件明确失败示例取证规则

Pricer合同可执行、方法允许、引擎已实现、市场输入完整、数值诊断通过。model_unsupported、market_input_missing、correlation_invalid、not_converged。失败时不得出现伪PV或伪Greeks。
Backtester数据覆盖完整、入场规则有效、观察日可映射、多标的可对齐。insufficient_tenor、observation_missing、alignment_failed、zero_valid_samples。零有效样本不能包装成0收益结果。
ReportRun显式运行引用存在、状态可用、合同与分析基准满足兼容规则、产物哈希正确。run_missing、evidence_mismatch、artifact_corrupt、audience_forbidden。不满足时拒绝正式客户交付并保存ReportRun Error。
结果对象固定内容不适用与错误表示

6.3 Payoffer：默认资料图与本次参数化图

80%主执行设计

普通运行只读本产品默认视觉JSON，用ResolvedContract覆盖本次条款，由共享解释器和SVG渲染器生成本次PayoffResult。

20%错误边界

资料库维护流

正常任务流

6.3.1 Payoffer独立构建规格

Payoffer只有一个正常运行入口render_payoff(PayoffInput)和一个严格隔离的管理员维护入口publish_default_assets。二者复用同一SVG渲染核心，但权限、输入和写入目录完全不同。普通入口永远不能调用发布函数；默认JSON只保存图形布局、路径面板、坐标、标注和参数绑定，不成为第二份收益公式。

6.4 Pricer：PricingConfig、模型路由与估值结果

80%主执行设计

将ResolvedContract、PricingConfig和market_data_refs解析为估值日前状态、市场快照与最终配置，按资格路由闭式解或Monte Carlo，再按请求输出PV、公平条款、Greeks、风险曲线、风险曲面、情景和数值诊断。

20%错误边界

历史状态缺失、引擎不支持、市场输入缺失、相关矩阵无效、求解无根或不收敛时输出明确诊断；禁止伪造PV、Greeks及风险网格。

Pricer不直接把合同、历史行情和用户覆盖散装传给某个模型。唯一输入先形成PricingInput，再依次解析估值日前已发生的合同状态、市场快照、最终配置和模型资格。执行价、障碍、票息、观察频率、锁定期和结算顺序只能来自ResolvedContract；市场假设、数值方法和风险分析请求只能来自PricingConfig与DataAssetRef。

PricingInput = { contract: ResolvedContract, pricing_config: PricingConfig, market_data_refs: [DataAssetRef] } ↓ ObservedContractState + MarketSnapshot + ResolvedPricingConfig ↓ PricingContext = { contract, observed_state, market_snapshot, resolved_config, engine_version } ↓ 基础估值 / 公平条款求解 / 点Greeks / 风险曲线 / 风险曲面 / 情景估值

估值日前状态与定价上下文

对起始日估值，ObservedContractState可以为空状态；对存续期中的雪球、累计期权、区间计息或其他路径结构，Pricer必须用合同起始日至估值日可见的不复权观察价格，通过共享解释器重放已发生事件，形成ObservedContractState={valuation_date、lifecycle_status、occurred_events、monitor_values、realized_cashflows、accrued_state、source_refs、state_hash}。该对象描述本次估值状态，不改写ResolvedContract。已经敲出、到期或结算的结构只估计尚未支付的合法现金流；历史覆盖不足时返回observed_state_incomplete，不得按“从未敲入或敲出”继续模拟。

MarketSnapshot保存估值日现价Stv、定价波动率σ、无风险利率Rf或折现曲线、分红率q或分红曲线、相关矩阵ρ及逐字段source。剩余期限τ由估值时点、合同到期和日计数规则派生，不是普通用户可随意覆盖的合同条款。

PricingConfig = { valuation_date, market_assumptions: { spot_override, volatility_source, volatility_override, hv_window, risk_free_rate_override, dividend_yield_override, correlation_override }, model: { model_method, process_model }, numerics: { path_count, random_seed, time_grid, variance_reduction, convergence_tolerance }, valuation_request: { target, solve_for_term, target_pv }, risk_request: { greeks, greek_bumps, scenarios, curves, surfaces } }

numericspath_count、random_seed、time_grid、variance_reduction、convergence_tolerance只控制数值计算并进入execution_fingerprint。路径产品的网格必须包含真实观察和支付时点；方差缩减方法只有引擎登记支持后才能启用。
valuation_requesttarget、solve_for_term、target_pvtarget默认为pv；可选公平票息、期权费或其他已登记条款求解。求解结果只作为报价建议返回，不原地修改ResolvedContract；不可求解字段返回unsupported。
risk_request点Greeks、扰动、情景、曲线和曲面的显式请求基础PV不强制计算全部高成本风险网格。轴、范围、点数、单位和最大计算预算必须显式；结构条款What-if会形成新的合同变体，不得伪装成市场Greek。

Black-Scholes-Merton

只在产品登记black_scholes、合同状态满足闭式假设且已有准确欧式闭式实现时使用。无法精确编译的结构必须拒绝闭式，不得以近似结果冒充闭式。

风险中性Monte Carlo

MC是路径结构的通用数值框架，不代表所有entry_status=True产品自动适用于GBM。只有合同、ObservedContractState、市场输入、随机过程和现金流解释均被当前引擎支持时才运行。

model_method=auto按照“精准闭式可用→闭式，否则已登记且已实现的MC→unsupported”选择。实际方法是OptionReg的pricing_methods、合同与ObservedContractState特征、Pricer Engine Capability、process_model及本次市场输入的交集。OptionReg只声明产品允许的方法，不保存模型数值参数；Pricer只登记真实实现能力，不以产品中文名称分支。

exercise_style是产品合同属性，留在OptionReg.terms。当前正式范围以欧式结算和按规则自动触发的结构为主；American虽可作为后续枚举，但在提前行权边界、数值方法和回归基准完成前必须返回unsupported。它不能因为Monte Carlo“理论上可模拟路径”就被声明为已经支持。

模型、现金流与数值口径

闭式引擎先实现标准欧式看涨和看跌的Black-Scholes-Merton公式；具体可绑定产品由model_capabilities.py和发布测试决定，不在总蓝图写死会漂移的产品编号。Monte Carlo在风险中性测度下模拟估值日之后的路径，以ObservedContractState作为起点，按真实观察日历调用共享解释器产生未来持有方现金流并折现。估值日前已支付现金流不进入未来PV；估值日现金流和待支付现金流按明确的估值时点与结算日程处理。

PV默认是持有方视角，并记录currency、notional_scale、quote_basis和含费口径。公平条款求解器反复调用同一估值引擎，使目标PV达到target_pv，返回求解值、残差、迭代次数和区间；它不能把求解结果写回合同。概率只输出经济定义明确且能从monitor或终态直接统计的指标。

Greeks、风险曲线、风险曲面与情景

点Greeks、曲线、曲面和情景不是四套模型，而是对同一PricingContext和同一估值引擎的不同调用。基础PV只运行一次；risk_request明确请求后，Risk Engine才创建受控扰动网格并重复估值。每个网格点都保存状态、模型版本、输入变化、PV、适用Greeks、标准误差和诊断；单点失败只标记该点，不能用插值伪造成成功值。

分析层正式内容适用边界
点GreeksDelta、Gamma、Vega、Theta、Rho；每项保存value、unit、scale、method、bump、standard_error和status。默认单位为Delta每1价格单位、Gamma每价格单位平方、Vega每1波动率百分点、Theta每日历日、Rho每1bp。多标的Delta和Vega为有序向量，Gamma为矩阵；未实现项为not_applicable。
风险曲线PV或Greek随单一风险因子的变化，例如Delta/Gamma对Spot、Theta对剩余时间、Vega对波动率、PV对Spot或波动率。横轴只能是已登记市场因子或估值时间；修改执行价、障碍、票息等属于合同What-if，必须生成新的合同变体。
风险曲面PV或Greek随两个风险因子的二维网格，例如Spot×时间、Spot×波动率或多标的Spot组合。默认用二维热力图和切片，3D仅在离线组件、可读性和性能验证通过后作为附加视图；不得强制每个产品生成。
情景分析具名Spot、波动率、利率、时间和相关性冲击后的PV、Greeks、事件概率与诊断。多标的冲击按ResolvedContract.underlyings有序传入；情景不覆盖合同条款，也不替代历史回测。

单标的MC初期使用共同随机数中心差分；以后若增加路径微分、似然比或AAD，必须作为Engine Capability登记并通过同一风险单位与基准测试。曲线和曲面点数受计算预算限制，MC风险网格必须复用可复现随机流并报告每点置信区间。ITM概率只用于定义明确的简单到期结构；KI、KO、累计数量或其他事件概率只有共享monitor可观察且结果定义完整时才输出。

6.5 Backtester：逐笔历史回放与通用+专属结果

80%主执行设计

按入场日冻结历史ResolvedContract，使用真实可见历史路径回放合同事件与现金流，先落逐笔账本，再产生通用统计和MetricProfile专属结果。

20%错误边界

数据覆盖不足、观察日无法映射、多标的对齐失败或零有效样本时拒绝生成假结果；禁止前视和未实现的净值曲线。

BacktestConfig只控制回测区间、入场规则、完整期限要求、缺失值处理、多标的对齐、收益率分母、统计频率以及可选的入场特征分组；历史数据以BacktestInput中的独立DataAssetRef传入，不在Config中重复登记路径。BacktestConfig不能改变任何合同条款。Backtester接收ResolvedContract，在每个入场日内部生成HistoricalResolvedContract，以真实不复权收盘价无前视回放；若请求HV分组，只使用入场日前的前复权收盘价计算，不参与合同结算。逐笔保存trade_contract_fingerprint，最终账本保存ledger_hash。

6.5.1 Backtester独立构建规格

Backtester只有一个正式入口backtest(BacktestInput)。运行先生成候选入场日，再为每个入场日冻结HistoricalResolvedContract，随后复用同一个路径回放器和共享解释器，最后从不可变逐笔账本计算公共统计和结构专属MetricProfile。逐笔现金流是唯一底层事实，任何汇总指标都不能绕过账本直接从价格序列估算。

组成目标文件职责可维护性规则
服务入口service.py校验BacktestInput、组织入场样本、运行回放、聚合指标并原子提交BacktestResult与账本。一次运行只有一条编排链；批量产品由上层创建多个ModuleRun。
入场与合同core/entry_generator.py、共享contract_resolver.py生成entry_date，并逐笔冻结参考价、合同日历、观察日程和trade_contract_fingerprint。入场规则属于BacktestConfig；合同观察规则仍属于ResolvedContract。
路径回放core/path_replay.py按可见历史价格顺序推进monitor，调用共享解释器选择path、case和现金流。不包含产品名称分支，不自行补KI/KO优先级。
逐笔账本core/trade_ledger.py保存每笔输入快照、事件、现金流、PnL、收益率、退出原因、数据标记和哈希。汇总前先完整落账；失败样本与跳过原因也必须可追溯。
公共统计core/common_metrics.py只从账本计算样本数、胜率、均值、中位数、极值、最大损失和分布。定义全局唯一，不由各MetricProfile重新实现。
专属指标core/metric_profiles.py、config/metric_profile_map.py按产品显式绑定一个或多个可复用Profile，从账本事件提取结构专属指标。新增Profile是小型纯函数；不把专属列塞入所有产品结果。
人工页面modules/backtester/page/中的HTML、CSS与JavaScript右侧上方显示ResolvedContract，下方显示BacktestConfig；中央按适用Profile展示统计、分布和逐笔表。不展示不适用指标，不生成尚未实现的净值曲线。

Backtester扩展与测试

  • 新增产品若现有路径解释和MetricProfile已覆盖，只增加产品映射和Golden ledger，不复制回放器。
  • 新增专属指标必须说明输入账本字段、数学定义、分母、适用条件、空样本行为和报告名称。
  • 测试覆盖入场边界、完整期限、月末与指定交易日、日度观察、缺失日、多标的交集、同日事件优先级和提前终止。
  • 逐笔PnL手工样例与共享解释器现金流逐项相等；汇总指标必须能由账本重新计算得到。
  • 任何动态入场参数只使用entry_date及以前数据，使用未来数据的测试必须明确失败。

7.Agent、模型网关与Recommender推荐模块

80%主执行设计

闲聊是交互形态，不是第七类业务Tool路由；闲聊中的实际请求仍分流到知识、数据、直接运行、推荐、报告和资料维护六类路由；只有推荐请求进入候选状态机。

20%错误边界

不得把模型推测写成用户事实，不得无证据推荐或无批准执行；模块失败、缺数或缺条款必须保留状态。

7.1 六类自然语言请求分流

请求至少分为六类：产品知识问答与比较、独立数据请求、指定结构或合同的单模块/多模块运行、结构推荐、已有结果的报告组装与导出、管理员资料维护。普通查询不应被多Agent流程拖慢；只有用户以市场判断、风险约束、期限或目标收益请求“推荐何种结构”时才进入Recommender。用户已指定产品或本次合同则直接进入受控执行链；已有ModuleRun只进入Reporter；资料维护必须进入管理员发布流程。

7.2 单Agent、多Agent与模型网关

Agent Runtime的所有者随产品封装变化：外部Skill Host拥有自己的模型、会话、上下文和通用Agent循环；OptionHelper App通过ModelGateway和App Agent Runtime支持DeepSeek、Kimi、Codex、Claude等模型。两者共同使用相同Tool Catalog、结构化输入输出、权限门禁、OptionLib受控检索和结果状态协议。模型不得凭记忆编造条款、声称已完成计算，或把任何凭据写入提示词和结果。

Recommender拥有的是“期权结构推荐”领域Workflow，不拥有通用聊天会话、模型Provider、任务队列或App权限。App Agent Runtime或外部Host决定何时调用Recommender；Recommender内部的Intent、Research、Critic和Executor只处理推荐领域状态。OptDesk直接运行已指定结构时不进入Recommender。

7.3 Recommender：候选、证据、合同与执行绑定

Recommender是具有独立模块目录、module-guide和Manager的编排模块，不是金融计算模块，由根Skill或OptChat调用。多Agent可按Intent、Research、Critic、Executor分工；单Agent不具备多Agent能力时，必须按同一顺序执行。Intent每轮最多问一个会改变候选、条款取舍或计算条件的问题。Research只能引用同一catalog_version下受控检索返回的OptionList和OptionLib片段；Critic只找反例、冲突和排除理由；CandidateSet必须先形成并完成用户确认或受控策略批准，Executor之后才能把已确认候选绑定为合同并调度模块。

推荐状态对象与四个固定角色

对象或角色必须保存或完成禁止行为
RecommendationCaseanalysis_case_id、task_id、tenant_id、用户原始描述、已确认目标、风险承受、期限、标的、市场观点、数据引用、缺失信息、catalog_version、requested_outputs和audience。把模型推测写成用户已确认事实。
Intent识别推荐目标和决定候选的缺口，每轮只问一个信息增益最高的问题。一次抛出长表单，或在未区分闲聊、直接运行和推荐时启动全流程。
Research按OptionList→OptionLib→OptionReg可执行状态→DataFetcher证据顺序检索；每个候选必须有product_id和OptionLib章节引用。用模型记忆、网络概述或默认图替代产品条款证据。
Critic核查适配假设、相反市场情景、结构风险、数据缺口和不可执行原因；保留一个主候选和最多两个有实质差异的备选。为了凑数量保留同质候选，或删除不利证据。
Executor只对已批准CandidateContract解析ResolvedContract，按请求调度DataFetcher及0至3个Payoffer、Pricer、Backtester运行并收集ModuleRunRef。在批准前运行昂贵模块、强制三模块全跑，或把candidate_run_id当ModuleRun.run_id。
RecommendationCase → CandidateSet（候选、依据、排除理由、数据与条款缺口） → 用户确认或符合策略的自动批准 → CandidateContract { candidate_id, term_overrides, evidence_refs } → ResolvedContract { contract_fingerprint } → 按需调用DataFetcher、Payoffer、Pricer、Backtester → RecommendationResult（候选、ModuleRun状态、结果引用、限制） → Reporter（仅在用户明确需要正式交付时）

candidate_run_id属于推荐编排记录，不能替代各模块独立的run_id。CandidateSet可以在数据未齐时成立，但RecommendationResult只能引用真实ModuleRun；自动批准策略必须由权限和产品规则明确配置，模型不能自行把候选视为已确认合同。

缺少决定性信息时先追问；可推荐但市场或合同输入缺失时，返回有来源的候选和缺口；模块失败或不支持时保留真实状态，不生成伪估值、伪回测或伪报告。

推荐结果至少回答七项：用户目标和已确认约束、主候选及适配理由、备选及其真实差异、被排除结构与理由、条款或数据缺口、各已请求ModuleRun的真实状态与引用、风险和下一步。候选状态必须区分candidate、pending_data、pending_terms、approved、running、report_ready、rejected和unsupported；“可推荐”不等于“已计算”，“已计算”不等于“可交易”。

7.4 Recommender独立构建规格

Recommender只有一个领域入口recommend(RecommendationCase)。单Agent与多Agent共用同一状态机和结构化中间对象，差别只在每一步由同一模型还是不同模型执行。不要为四个角色各建一套数据库、服务和结果格式；角色是Workflow步骤，不是四个永久子系统。

组成目标文件职责边界
服务入口service.py创建RecommendationCase、推进状态、处理暂停与恢复、提交RecommendationResult。不拥有通用会话；外部Host或App传入conversation_ref。
请求分流core/intent_router.py区分知识问答、数据、直接运行、推荐、报告和资料维护，并提取推荐必要缺口。不是推荐请求时立即返回目标Tool，不强制进入多Agent。
证据检索core/evidence_retriever.py固定catalog_version，按OptionList和OptionLib返回带product_id与章节定位的证据。模型不直接扫描未发布文件，也不以网络概述替代产品库。
候选与批判core/candidate_builder.py、core/candidate_critic.py形成少量有实质差异的候选，记录适配、反例、排除、数据和条款缺口。Critic不能新增产品或改写合同；CandidateBuilder不能伪造运行结果。
执行器core/executor.py只对已批准候选解析合同，按requested_outputs调用DataFetcher、Payoffer、Pricer、Backtester并收集引用。通过Tool API调用，不导入模块内部Python文件。
Agent适配core/agent_steps.py、config/recommender_config.py定义Intent、Research、Critic、Executor步骤的结构化输入输出、提示模板版本、超时和最大候选数。模型Provider属于外部Host或App ModelGateway，不写入Recommender。

Recommender扩展与测试

  • 新增产品进入CatalogVersion后自动成为可检索候选，不需要修改推荐代码；是否可执行由entry_status和模块能力决定。
  • 新增推荐策略只能改变筛选或排序证据，不能改变合同条款、市场数据和模块结果。
  • 单Agent与多Agent对同一结构化步骤应满足相同Schema、状态转换、候选证据和审批门禁。
  • 测试覆盖闲聊不误入推荐、一次只问一个关键问题、数据缺口、条款缺口、候选批准、模块失败、报告未请求和权限不足。
  • 每个候选必须可回溯product_id、OptionLib章节、catalog_version和明确排除理由。

本模块文档：modules/recommender/module-guide.md规定何时调用Recommender、步骤、暂停恢复和结果解释；recommender-manager.md维护状态机、角色契约、提示模板、候选策略、评测集和模型兼容。产品介绍和推荐话术不复制进Manager。

8.Reporter报告模块、Designer设计模块与交付体系

80%主执行设计

Reporter显式解析已选证据和ModuleRunRef，冻结ReportUnit后先选择Card简单版或Report详细版，再由Designer输出HTML或PDF，不重算金融结果。

20%错误边界

证据缺失、合同不匹配、受众越权、产物损坏或格式转换失败时拒绝正式交付；不自动选“最新”运行。

8.1 Reporter：ReportUnit、ReportBundle与显式取证

80% Reporter主线

ReportRequest给出主题和显式source_refs，Reporter逐一重新鉴权、校验合同与哈希、构建不可变ReportUnit，再调用Designer与导出器。

20% Reporter边界

不重算、不合并不同合同、不自动选最新Run、不将失败模块包装成已完成证据。

Reporter是结果整合与交付Skill，不是第四个计算引擎。ReportRequest必须明确subject_type和source_refs；模块证据只提交ModuleRunRef={tenant_id、task_id、run_id、expected_semantic_result_hash}，由ResultStore解析canonical结果并重新鉴权，调用者不得提交result_dir。analysis_case_id始终存在，candidate_id仅在Recommender流程中可选关联；task_id只用于组织，不单独证明经济一致性。

ReportRequest = { analysis_case_id, subject_type: "product" | "contract" | "bundle", subject_ref, source_refs: { product_version_refs, catalog_version_ref, evidence_refs, module_run_refs }, output_type: "card" | "report", format: "html" | "pdf", html_report_layout: null | "with_toc" | "continuous", audience }

output_type先决定内容是Card简单版还是Report详细版，format再决定输出HTML或PDF。只有output_type=report且format=html时，html_report_layout才可选择with_toc或continuous；PDF Report采用无左侧目录的PDF阅读版，Card不使用报告版式字段。

ProductKnowledgeUnit

用于产品学习Card。可只冻结product_version、OptionLib证据、默认资料图、风险和来源，不要求candidate_id、ResolvedContract或ModuleRun。

ContractReportUnit

用于本次合同分析。一个Unit只对应一个标的组合、一个结构和一个ResolvedContract；所选Payoffer、Pricer、Backtester结果必须属于该合同且逐项验证。

ContractReportUnit固定对象

ContractReportUnit = { report_unit_id, analysis_case_id, task_id, candidate_id?, report_version, generated_at, audience, evidence_status, subject: { product_id, name_zh, product_version, resolved_contract_ref, contract_fingerprint, currency }, underlying_context: { asset_ids, display_names, underlying_order, underlying_rule, as_of_date, market_spots, market_reference_prices, normalized_spots }, recommendation: { fit_summary, recommendation_reason, suitability_conditions, not_suitable_for, key_risks, evidence_refs }, terms_snapshot: { resolved_terms, term_sources, resolved_schedules, holder_side, observation_rule, cashflow_rule }, module_evidence: { payoffer?: { module_run_ref, input_snapshot, status, result_ref, artifact_refs }, pricer?: { module_run_ref, input_snapshot, status, result_ref, market_snapshot_ref }, backtester?: { module_run_ref, input_snapshot, status, result_ref, trade_ledger_ref } }, provenance: { data_asset_refs, parameter_overrides, symbol_mapping, model_versions, template_version, assumptions, limitations, disclaimer_version }, semantic_fact_hash }

问号字段只表示合法可空，不表示可以省略其状态。没有运行某模块时，module_evidence必须记录not_requested；已请求但失败时保存对应ModuleRunRef、状态和Error。ReportUnit不复制物理结果目录，所有结果和产物均以受控引用及预期哈希解析。

固定基数：ReportUnit以subject而非同一task_id为边界。多个产品、多个标的组合或多个合同使用ReportBundle组合多个有序ReportUnit，不能在一个ContractReportUnit中混合不同合同的PV、Greeks或回测结果。

Reporter不要求不同模块的execution_fingerprint相等，而是验证每个ModuleRun自身执行指纹完整，并核对product_version、contract_fingerprint、analysis_basis_id、产品身份、标的顺序、价格口径和必要数据基准兼容。它不得搜索“最新一次”结果、重跑模块，或用默认资料图和案例数值替代本次运行。

证据组合由用户请求决定，不强制三模块全跑。普通聊天中的临时文字或附件可以直接返回，但任何需要保存、导出或复用的Card或Report都必须由Reporter冻结为ProductKnowledgeUnit或ContractReportUnit，再调用Designer。Card只裁剪允许的核心字段；Report保留完整证据、参数、错误、缺口和未运行状态。销售用户默认只能生成Card，管理员可生成Card或Report。

校验项必须一致的内容不满足时
合同与执行可空candidate_id、product_version、contract_fingerprint、analysis_basis_id、产品编号、中文名称、标的顺序、币种和价格口径；每个ModuleRun自身execution_fingerprint有效。拒绝合并金融数值；内部草稿可标记mismatch及原因。
产物ModuleRun清单与各引用SVG、结果JSON、逐笔账本、图表的ArtifactManifest及哈希。标记corrupt或stale，不能对外生成完整报告。
事实已运行模块的状态、市场与数据来源、限制、研究来源和风险提示。按真实状态展示，不能补写默认数值或图形。

ReportRun拥有独立状态机：created→validating→rendering→succeeded/partial/failed/cancelled/timed_out。它保存ReportRequest、证据引用、冻结ReportUnit或ReportBundle、designer_input、design_system_version、审批与受众状态、ArtifactManifest和Error；重试必须生成新的report_run_id。

Reporter九步固定流程

  1. 校验CallerContext、audience和ReportRequest外形。
  2. 通过ResultStore解析每个显式ModuleRunRef并重新鉴权，禁止扫描目录或选择“最新”。
  3. 校验产品发布、合同指纹、标的顺序、币种、价格口径、analysis_basis_id、semantic_result_hash和产物哈希。
  4. 区分ProductKnowledgeUnit、ContractReportUnit和多Unit的ReportBundle，拒绝跨合同混合数值。
  5. 按output_type选择Card简单版或Report详细版，不重算PV、Greeks、回测或收益图。
  6. 冻结结构化ReportUnit、来源、限制、不适用项及审批状态，计算事实哈希。
  7. 生成designer_input并调用Designer Renderer；Designer只能改变表达。
  8. 按format生成HTML或PDF；仅HTML Report校验html_report_layout、目录、链接、图表和可访问性。

8.1.1 Reporter独立构建规格

Reporter只有一个入口build_report(ReportRequest)。它先解析和冻结证据，再选择内容Profile，最后把只读DesignerInput交给Designer。证据解析和页面渲染必须分开，因此替换HTML模板不会改变ReportUnit，模块结果变更也不会被旧页面缓存掩盖。

8.3 Designer：全局设计系统与报告渲染约束

80% Designer主线

正式视觉方向：报告、Card、模块页面和App采用简洁、克制、专业的光大红金白体系。白色与近白色承担主要阅读面，光大红用于品牌、关键操作与核心事实，金色只用于风险阈值、提示和少量强调，正文与数值以深色高对比呈现。避免大面积渐变、过多卡片、装饰性小字、无意义阴影和炫技动效；高级感来自精确排版、留白、细线、数据层级和一致图表。

9.6 OptionHelper App与模块页面构建规格

App由平台壳层和共享Capability两部分组成。平台壳层负责账号、权限、会话、模型、任务、密钥、存储、审计和页面挂载；共享Capability来自已验证的capability/option-helper/。开发初期使用本机Provider实现同一端口，正式服务器只替换Provider，不重写页面、Skill或金融模块。

组成正式职责与本机阶段的关系禁止事项
App ServerHTTP入口、静态资源、Tool Gateway、Module Host和健康检查。本机可单进程启动；服务器可拆分部署但API不变。不直接实现定价、回测或报告。
Identity与Authorization账号、会话、销售用户/管理员角色和逐Tool capability裁决。本机使用LocalAuthProvider授予明确开发能力；接口从第一天与服务器一致。不能根据前端隐藏或模型自述角色授权。
ModelGateway与Agent Runtime适配DeepSeek、Kimi、Codex、Claude等模型，管理上下文、工具循环、超时和用量。开发期可使用本机环境变量或Keychain背后的SecretProvider；正式期切到服务器密钥服务。模型凭据不得进入浏览器、提示词、ModuleRun或仓库。
Settings Service统一管理模型Provider、数据Provider、Store、导出路径、缓存和个人偏好的非敏感配置，并提供连接测试。开发期写本机配置与系统凭据引用；正式期读写服务器配置策略与Secret引用。不保存明文密钥，不把合同条款或模块Config变成全局设置，不允许销售用户修改管理员策略。
Task Runtime创建AnalysisCase、调度Tool、取消、重试、状态推送和并发限制。本机可同步或轻量队列；对象和状态机与服务器一致。不能用会话消息代替正式任务状态。
OptChat对话、附件、Card、Report、Run状态和外部Host等价工具调用。使用App Agent Runtime；根SKILL.md提供OptionHelper领域路由。不保存第二套产品库或模块结果。
OptDesk管理员任务索引、合同与Config编辑、唯一模块页面挂载、结果选择和报告组装。通过Module Page Registry加载Capability内五个页面的同一build hash。不复制模块HTML、字段Schema和计算逻辑。
Stores与AuditDataStore、ResultStore、会话、任务、审计和导出的租户隔离实现。本机实现写受控本地目录；服务器实现写数据库或对象存储。调用方不能提交任意物理路径绕过storage_ref。

App与独立模块页面的统一方式

  1. 每个可操作模块只构建一次HTML/CSS/JS，产生唯一build hash。
  2. LocalModuleHost与AppModuleHost只注入不同ModuleHostContext，不修改页面源码。
  3. 页面根据capability token显示可操作项，但每个API仍在服务端重新授权。
  4. 机器调用直接使用Tool API，不需要打开HTML；页面也只能通过同一API运行模块。
  5. 本机Provider和服务器Provider必须通过相同契约测试后才能切换，确保封装变化不改变金融结果。

App文档：products/app/app-manager.md是平台唯一管理文档，记录身份、权限、模型、任务、Provider、前端挂载、发布和回滚；根SKILL.md不描述App内部实现。OptChat和OptDesk若需要开发说明，放在各自开发文档，不再建立能够改写业务规则的Manager。

10.2 凭据、敏感信息与审计边界

前端隐藏不是安全边界。AuthorizationPolicy在服务端和工具网关执行；SecretProvider负责模型和数据源凭据；ModuleRun、ReportUnit、前端静态文件、OptionReg、Git和模型上下文中不得出现Token、密码或私钥。许可套餐决定哪些产品能力可用，用户角色决定允许执行哪些业务动作，二者不互相替代。

ModuleRun、ReportRun、DataAssetRef和ReportUnit必须携带tenant_id、created_by与access_scope，由DataStore和ResultStore执行对象级授权，物理文件路径不能作为权限依据。审计事件最小字段为actor、tenant、action、resource_ref、decision、reason、timestamp、request_id、before_hash和after_hash；留存期限由服务器治理策略确定，但任何日志均不得记录明文凭据。

必须记录的安全事件：授权拒绝、资料维护、默认资产发布、数据源调用、导出、报告复核、模型工具调用失败和超时，以及设置创建、修改、删除、连接测试、Secret引用更新、Provider启停与优先级变化、Store或导出策略变化。记录before_hash、after_hash、操作者、租户、权限决策和时间，不记录明文凭据。

80%主执行设计

ResultStorePort以不可变manifest、输入快照、canonical结果、产物和哈希保存DataFetchRun、ModuleRun和ReportRun；对话与页面只保存RunRef。

20%错误边界

任何缺少必需文件、哈希不一致或原子提交失败均不得标记成功；用户指定路径只是受控导出副本。

11.1 五类不可变结果目录

result/ ├─ output_datafetch/{task_id}/{data_fetch_run_id}/ ├─ output_payoff/{task_id}/{run_id}/ ├─ output_pricing/{task_id}/{run_id}/ ├─ output_backtest/{task_id}/{run_id}/ └─ output_report/{task_id}/{report_run_id}/

11.3 OptChat、OptDesk、报告库与用户指定路径

外部Host、OptChat与OptDesk只保存会话任务、消息、状态、RunRef、附件和哈希，不复制数据或金融事实。用户可以选择临时交付目录，但该动作仅从已经存在的DataFetchRun、ModuleRun或ReportRun导出副本或打包；canonical结果不移动、不被导出路径取代。导出目标必须通过允许目录校验，默认不覆盖同名文件，冲突时生成带时间与短哈希的新文件名；先写临时文件、核对哈希后原子完成，并生成export_manifest。外部副本可回溯，但不成为后续计算或Reporter读取的事实来源。清理只删除达到留存期且无活跃引用的缓存或失败暂存；已提交Run、报告、版本历史和审计引用不得由普通用户清理。

跨平台事实：“一键生产Skill和App”指在当前平台一次完成标准Skill与该平台App。macOS不能直接签发Windows安装物，Windows也不能直接签发macOS安装物；正式双平台发布由macOS和Windows构建机分别执行同一build_all.py，再把两份平台产物汇总到同一app_version历史目录。平台差异不能改变Capability内容。
通用Skill锁定：option-helper是唯一可安装、可被任意兼容宿主发现的标准Skill，唯一发现入口是根SKILL.md。发行包不包含任何模型厂商专用目录、配置或元数据；模型、对话上下文与Agent框架均由宿主提供。DataFetcher、Recommender、Payoffer、Pricer、Backtester、Reporter、Designer在业务上可称子Skill，技术上是根Skill内部能力模块。只有DataFetcher、Payoffer、Pricer、Backtester、Reporter拥有操作页面。
当前实施边界：12.1目录迁移已建立，旧assets/业务实现已进入只读历史区，正式运行源收敛到core/与modules/。这不代表后续工作包的业务功能已经完成。assets/web-design/只保留冻结参考；未来迁入App的仅为登录、OptChat、OptDesk和统一设置中心壳层，五个模块页面必须继续来自Capability。

14.明确不在本阶段擅自固化的事项

下列问题必须在后续具体对话中明确后再实现。本蓝图登记它们的归属，避免任何对话根据猜测改写核心规则。

服务器与多用户

任务队列、并发、取消、超时、资源上限、多租户隔离、审计留存、备份和灾备属于正式服务层设计，不应由单机模块自行决定。

数据授权与缓存有效期

iFinD/Wind的字段授权、额度、缓存刷新、企业行动修订、数据冲突和用户上传留存期需随数据合同单独确定。

对外发布与合规

evidence_verified不等同human_reviewed，更不等同可交易。报告审批、免责声明版本、报价审批和销售话术边界需业务流程确认。

模型能力与成本

多模型路由、限流、重试、费用、上下文脱敏、工具审批和故障降级属于ModelGateway策略，不属于单一Agent提示词。

美式行权与扩展模型

当前优先欧式闭式与风险中性MC。未来美式行权、局部波动率、跳扩散或交易对手信用调整应扩展Pricer接口后独立验证。

跨标的商业定义

多标的合同、相关性、缺失对齐、Worst-Of或Best-Of的产品条款需由OptionLib与OptionReg逐产品明确，不可由回测或渲染层补充。
